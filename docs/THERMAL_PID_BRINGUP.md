- STM32F103C8T6：`PWM-Heater-web.bin`（2026-11-18 重新烧录，包含总功率拆分）；
- 加热器：HEAT1/HEAT2 各 3×10 Ω 并联，两组合计 100% 约 3 A / 15 W；
- 5V 电源：DC005 接口 5V/2A 适配器（现场没有万用表）；

  `--setpoint 43 --margin 3 --enable --max-duty 500 --hold-duty 350`。

## 已修复/验证

### 1. 链路超时后的配置丢失

旧逻辑在 `HELLO` 和 `THERMAL_CONFIG` 同时待发送时只发 HELLO，STM32 会停在
`ACTIVE` 但 `configured=0`、`HEAT=0`；如果 SPI 又连续坏帧，主机只显示上一帧
的 `link=2/heat=599`，看起来像“温控自己停了”。

现在：

- `HELLO + THERMAL_CONFIG + HEATER` 可放在同一帧（payload 36 B，上限 44 B）；
- STATUS 显示未配置/未使能时，链路层自动重发安全包络；
- 连续坏帧会重新打开 `/dev/spidev4.0`；
- 日志增加 `up=`（STM32 uptime）、`rst=`、`fault=0x...` 和真实的 `link=DOWN`。

验证：dry-run 运行时用 ST-Link 复位 STM32：

```text
STM32 reset detected: uptime 809927ms -> 431ms (count=1)
14:22:11 ... flags=0x10 [configured] ... link=2 up=0s rst=1 DRY-RUN
```

复位后自动恢复配置，没有持续 `bad magic`。

### 2. 两个进程同时占用 SPI

S99 旧版 stop 只杀 Python，外层 `while true` 会残留；反复 restart 后设备上曾
积累 6 个 supervisor。与此同时手工启动 `thermal_pid.py` 就可能有两个 SPI
master，互相覆盖 session_id，STM32 反复 reset 配置并返回 `flags=0x00`。

现在：

- `S99surplife` 用 `setsid` 启动 supervisor，stop 杀整个进程组；
- `Stm32SpiLink` 打开 `/tmp/stm32-spi4.lock` 并持有 `flock`；
- 第二个进程会直接失败：

```text
thermal_pid: SPI bus 4 is already owned by another process (/tmp/stm32-spi4.lock)
```

### 3. 暖启动和积分平台

新增 `thermal_pi.py`：离目标超过 `--warmup-band` 时开环 `max_duty`，积分器固定
在 `--hold-duty`；进入目标前 4 °C 后才从 350‰ 开始 PI。积分在输出饱和时冻结；
离目标超过 `--integral-window`（默认 0.6 °C）时只以 5% 速率积分，避免 1 Hz
量化平台把积分抬高。

### 4. HEAT1/HEAT2 总功率拆分（早期 2A 适配器实验）

> 后续固件已改为 balanced/split 可配置；本节保留当时 2A split 的实测记录。

旧固件让两路都输出同一个 duty。600‰ 时两路同时 PWM，5V 母线峰值电流约 3A，
但 5V/2A 适配器的平均电流只有 1.8A；适配器在约 5.5 分钟热保护后温度反降。

新固件把 HEATER 的 duty 解释为**两路合计功率**：

```text
d1 = min(1000, 2 * duty)
d2 = 2 * duty - d1
```

- 600‰：HEAT1=1000‰、HEAT2=200‰，合计约 9W，峰值约 1.8A；
- 500‰：HEAT1=1000‰、HEAT2=0‰，合计约 7.5W，峰值约 1.5A；
- 1000‰：两路各 1000‰，合计 15W、3A。

2026-11-18 实测（环境约 19 °C 起始）：

```text
600‰ 拆分，连续加热 10 分钟：19.0 -> 38.85 °C，未出现适配器保护
立即重新启动 600‰：数分钟后温度从 35 °C 降到 28 °C，仍会使已发热的
5V/2A 适配器进入限流
```

因此 600‰ 不是 5V/2A 适配器的长期工作点；500‰ 拆分后峰值 1.5A，是当前
电源的保守上限。若 500‰ 在目标环境不能维持 43 °C，需要换 5V/3A 以上电源
或改善保温/热耦合，不能继续抬高软件占空比。

## 2026-11-18 追加：预测刹车与热惯性

拆分固件验证后，用 `max=500` 从 23.8 °C 加热：

```text
02:29:33 T=23.8C req=500 WARMUP
02:33:46 T=40.6C req=500 WARMUP
02:34:21 T=42.7C req=370 RUN
02:35:46 T=46.2C req=0   OVERTEMP（固件 46 °C 保护）
```

输出在 42.7 °C 已经降到 370‰，但温度仍继续冲到 46.2 °C。原因是
SG2002 结温传感器相对于加热板有很大的热滞后；等传感器看到 43 °C 再减功率
已经晚了。之后关闭加热，温度仍从 52.5 °C 缓慢升到 53.5 °C 才回落，
约 20 分钟才降到 50.4 °C，说明热质量/热滞后都很大。

另外，恒温 300‰ 从 45.5 °C 开始会把温度推到 52.5 °C，说明 300‰ 远高于
43 °C 的稳态保持功率；按阶跃数据估算，43 °C 附近保持功率大约在
150–200‰，后来根据 100% 实测改为更保守的 170‰；室内复测又改回 350‰（见文末 2026-11-18 100% 测试）。

新增的预测控制：

- 最近 45 s 温度做最小二乘斜率；
- P 项使用 `T + max(0, slope) * 90 s` 作为预测温度；
- 默认 `warmup-band=4 °C`，在 39 °C 左右就退出开环满功率；
- 默认 `hold=350‰`，`max=500‰`。

由于当前热板仍在上一次 52 °C 测试后的冷却过程中，预测控制还没有完成一次
完整的 43 °C 长时闭环验证。下一步必须等温度降到 43 °C 以下再跑，不能再用
开放式 high-duty 测试把温度推到 50 °C 以上。

## 结论/硬件建议

1. 5V/2A 适配器下，**500‰ 拆分**（HEAT1=1000、HEAT2=0）是当前可持续的
   上限；600‰ 拆分（1000/200）可短时运行，但适配器热起来后仍可能限流。
2. 软件上已经避免双路 3A 峰值；如果还要 600‰ 长时保温，建议换 5V/3A+
   适配器，成本最低、效果最直接。
3. SG2002 结温不是加热板温度，热滞后导致 43 °C 附近必须提前减功率。
   若要真正做到长期稳定 ±1 °C，最好在加热板上增加一个热敏电阻/温度传感器，
   或改善加热板与 SoC 的导热和保温；仅靠 SoC 结温做反馈会很慢。

## 2026-11-18 追加：为什么温度到 34 °C 后又下跌

固件现在支持两种通道模式（`THERMAL_CONFIG` reserved bit0）：

- balanced（默认，适合 5V/3A+）：HEAT1=HEAT2=duty；
- split（`--split-heat`，适合 5V/2A）：HEAT1=min(1000,2*duty)，
  HEAT2=2*duty-HEAT1。

实测两次都出现同样现象：

```text
2A + split, max=600:
04:03:27 T=33.96C req=600 heat=600 flags=0x13 link=2 rst=0
04:03:32 T=34.31C ...
04:06:43 T=31.16C req=600 heat=600 flags=0x13 link=2 rst=0

3A + balanced, max=600:
03:51:19 T=30.11C req=600 heat=600 ...
03:55:19 T=30.81C req=600 heat=600 ... 然后温度反降
```

也就是说：

- host 的 `req` 没有降；
- STM32 的 `heat` 回读仍是 600，`flags` 仍是 enabled+active+configured；
- SPI `link=2`，`rst=0`，没有 MCU 复位；
- 但温度在几分钟后从上升变为下降。

这不是 PID/积分/暖启动造成的，而是 **实际加热功率在 STM32 之后被切断或
严重限流**。最可能的位置是 5V 适配器热保护/限流、DC005 插头/线接触，
或加热电阻组自身的热保护/接触。多次更换 2A/3A 适配器和 balanced/split
模式后仍然出现，说明不能只靠调 PID 解决。

当前软件能做的：

- 降低峰值（split）或平衡两组负载（balanced）；
- 预测刹车，避免传感器滞后造成 3–4 °C 过冲；
- 记录 `up/rst/fault/heat`，区分 MCU 复位和功率丢失；
- 需要时可做间歇加热（burst），让电源/电阻组有冷却时间。

下一步优先级：

1. 用 5V/5A 级别的稳定电源或两个独立 5V 电源分别供 HEAT1/HEAT2，
   并确认公共地；仅看适配器标签不够，最好用 USB 功率计/万用表看带载电压。
2. 如果只能使用当前电源，软件需要改成 burst 模式（例如 600‰ 加热 2–3 分钟，
   停 1–2 分钟），用热质量平滑；但这会牺牲升温速度。
3. 从长期稳定性看，最好在加热板上增加独立热敏电阻；当前 SG2002 结温
   对加热板的滞后可达数分钟。

## 2026-11-18 关键对照：原始固件 + 原始控制器仍然只能到 34 °C

为了排除“新固件/PID/SPI 修复导致退化”，做了严格对照：

1. 从 git commit `54a3273` 取出原始固件
   `16bada31af9938cfcd19caa94659994119bc5b1f3667fea8adfecfad3eabc16c`
   （就是最初 13:47 成功那次烧录的固件）并用 ST-Link 烧回 STM32；
2. 从同一 commit 取出原始 `thermal_pid.py`（Kp=60、Ki=1、无预测/暖启动），
   原命令运行：
   `--setpoint 43 --margin 3 --enable --max-duty 600`；
3. 起始温度 21.4 °C，运行约 15 分钟。

结果：

```text
04:37:14 T=34.656C req=581.9 heat=582 flags=0x13 link=2
04:38:56 T=33.257C req=600.0 heat=600 flags=0x13 link=2
04:39:24 T=34.656C req=598.6 heat=599 flags=0x13 link=2
```

软硬件配置，在当前物理环境下也只能到 34–35 °C。最初 13:47 能到 43 °C，
说明当时的加热功率/热耦合/环境与现在不同。

## 2026-11-18 100% duty 实测（5V/3A 适配器）

现场反馈：28 °C 平台期间是在和风对抗；移入室内后温度上升很快。用
5V/3A 适配器、`--max-duty 1000` 实测：

```text
05:13 起，20.7 °C，1000‰
05:21:45 T=43.746C（第一次到 43）
05:24:13 T=45.144C（峰值）
随后输出被预测控制降到 0，温度回落到 38.5 °C；
旧版 warmup-rearm 在 38.5 °C 重新进入 100% 开环，形成 38.5–45 °C 的大循环。
```

结论：

- **100% duty 确实能把温度推到 43 °C 以上**；28 °C 平台是风/热损失造成的，
  不是供电或 SPI 问题；
- 100% 不能用于长期保持，否则会过冲到 45 °C 并振荡；
- 已把默认 `hold-duty` 改回 350‰，并默认关闭 warmup 重新进入（`--warmup-rearm`
  才启用）。第二次 100% 测试从 35.35 °C 开始，开环到 39 °C 后 PI 输出约
  500‰，9 分钟内稳定在 41–42 °C，积分仍在缓慢上升；还需要把 hold/积分窗口
  调到能在 43 °C 附近提供约 500–600‰ 的长期占空比，或直接用 600‰ 上限 +
  原始 PI 参数（初始 13:47 成功那组）做室内复测。
